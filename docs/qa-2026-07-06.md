the standing tests hit the stable API surface, so they survive the move.

## Ranked bug list

### BUG A (MEDIUM-HIGH): `/api/compliance` and `/api/overview` 500 on a fresh deploy
- Locus: `kairos_api/dashboard_api.py::_build_compliance`, fallback branch, the
  `retention_floor` check: `summary["average_retention"] >= settings.min_retention_floor * 100`.
- Repro: with no weekly CSV on disk `_plan_guardrail_items()` is empty, so the
  code falls to this branch; `_summarize_schedule(empty)` returns
  `average_retention: None`, and `None >= 72.0` raises
  `TypeError: '>=' not supported between instances of 'NoneType' and 'float'`.
  Reproduced by forcing `_plan_guardrail_items` empty and calling
  `_build_compliance(pd.DataFrame(), KairosSettings())`. Both `/api/compliance`
  and `/api/overview` (which calls `_build_compliance`) 500 on that state, which
  is exactly the "fresh deploy, or post-upload pre-recompute" case the
  `_summarize_schedule` docstring says it handles honestly.
- Pinned by: `tests/test_qa_known_bugs_20260706.py::test_compliance_fallback_survives_an_empty_schedule` (xfail strict).
- Suggested fix: treat `average_retention is None` as unknown, not a violation:
  set the check status to a neutral state (or `at_risk` with `observed: None`)
  instead of comparing None, mirroring the null-safe treatment `_summarize_schedule`
  already applies to `projected_revenue`/`risk_score`.

### BUG B (MEDIUM): `/api/inventory` and `/api/campaigns` fabricate revenue = 0
- Locus: `kairos_api/catalog_api.py::_build_inventory` (line ~163) and
  `_build_campaigns` (line ~199): `_series(frame, "revenue_ils", 0)`, fed by
  `kairos_api/core.py::_load_spots` which prefers `data/reference/Spots.xlsx`.
- Repro: the loaded frame (`_load_spots()`) has 50,386 rows and no `revenue_ils`
  column, so `_series` fills zeros and `/api/inventory` reports
  `summary.revenue: 0.0` and every `by_channel` row `revenue: 0`;
  `/api/campaigns` reports `revenue: 0` for all 50 campaigns. The same 50,386
  spots in `data/Spots.csv` carry `revenue_ils` summing to ~306,936,788.47 ILS.
  The zero is presented as measured, a Law-9 fabricated zero.
- Pinned by: `test_inventory_does_not_report_a_fabricated_zero_revenue` and
  `test_campaigns_do_not_all_report_a_fabricated_zero_revenue` (xfail strict).
- Suggested fix: when the loaded source has no `revenue_ils` column, either join
  the priced spots (the legacy `data/Spots.csv` has real `revenue_ils`) or report
  revenue as unavailable with a reason, never a hard 0. `_series` is the wrong
  tool for a money column whose absence should be disclosed, not zeroed.

### BUG C (MEDIUM): the `/effect` preview does not run under the saved settings
- Locus: `kairos_api/constraints.py::constraint_effect` and
  `kairos_api/overrides.py::override_effect`. Both call `optimize_breaks(segments)`
  and `optimize_breaks(segments, overrides=...)` with no `guardrails`, no
  `revenue_weight`, no `risk_lambda`, no `objective_mode`, and build segments with
  `PricingModel.from_yaml()` (ignoring `settings.pricing_overrides`). The
  optimizer defaults are `revenue_weight=0.5`, `guardrails=None`,
  `objective_mode="blend"`.
- Repro: the weekly recompute uses the saved `revenue_weight` (0.60), the saved
  `Guardrails`, the saved `objective_mode`, and `pricing_from_settings`. On real
  reference data for קשת 12 on 2024-11-06 the preview baseline optimizes to
  3,977,084.82 ILS while the recompute writes 4,002,181.49 ILS, a >25k ILS gap.
  The `constraint_effect` docstring claims "the deltas are exactly what the
  weekly recompute would write"; the absolute before/after revenue it reports is
  computed on a different plan, and on a channel-day where the daily/hourly cap
  binds differently at weight 0.5 vs 0.6 the break-count deltas would diverge too.
  (The within-call delta direction is preserved because both legs share the same
  wrong baseline, so this is a misstatement of magnitude, not always of sign.)
- Pinned by: `test_effect_preview_matches_the_recompute_plan_revenue` (xfail strict).
- Suggested fix: thread the saved settings into both preview legs, exactly as
  `recompute_api._run_recompute` and the golden path do: `_settings_to_guardrails`,
  `revenue_weight/100`, `risk_lambda`, `objective_mode`, and `pricing_from_settings`
  instead of `PricingModel.from_yaml()`.

### LOW (cleanliness): stale golden numbers embedded in a docstring
- Locus: `tests/golden_weekly_schedule.py::settings_map` docstring (line ~62)
  holds a full per-channel-day aggregate block whose values are the pre-adoption
  golden (for example קשת 12 2024-11-06 = 4,002,181.48, the bare-defaults figure,
  not the live 4,095,805.69). The function only does `json.loads(SETTINGS_PATH...)`,
  so the block is dead text and never parsed, but it reads as an authoritative
  baseline and will mislead the next reader.
- Suggested fix: delete the stale block from the docstring; the live baseline is
  the module-level `GOLDEN_AGG`.
