# P9 Kai: the published contract

The section 8.8 publication for P9: the endpoints it owns, the payload shapes it
emits, the files from section 8.2 it writes, and the helper module names it
creates. Frozen on delivery.

The piece serves JS-10, anyone asking in Hebrew from any surface and having it
act with preview and undo, against the reference in `07-references.md` section
7: the agent is embedded in the surface it acts on, it shows a concrete diff
with a preview control before anything lands, and the reversal is an object you
can point at and inspect rather than a single step.

## 1. Endpoints owned

All of them under `/api/assistant`, all pre-existing. **This round publishes no
new path and changes no response key set.** The OpenAPI surface P9 contributes
is unchanged, so nothing in this piece can shadow another piece's append.

| Method and path | What it does |
|---|---|
| `GET /api/assistant/status` | availability, model name, action-plane state |
| `POST /api/assistant/ask` | the ask, non-streaming |
| `POST /api/assistant/ask/stream` | the ask, as server-sent events |

## 2. Payload shapes this round changed, both additive

**The ask body key set is frozen and did not move.** It stays exactly
`available, answer, model, grounding, context_disclosure, truncated, error,
proposals, tool_trace, conversation_id`, which three test files outside P9's
ownership pin by equality. Everything new is carried on the stream's own stage
channel or on the batch, neither of which is pinned.

### 2.1 A proposal batch carries the restore points it produced

`GET /api/assistant/proposals` and the conversation changes view now return, on
a batch that has been applied at least once:

```json
"restore_points": [
  {"restore_id": "003e3283dba6",
   "applied_at": "2026-08-01T09:24:34.401832+00:00",
   "applied_by": "auth-disabled",
   "item_ids": ["c18528152928"]}
]
```

Oldest first, one entry per apply. A batch whose approved items touch no state
file (a plan run) produces no snapshot and carries no key at all. The apply
response still returns `restore_id` exactly as before.

### 2.2 The stream's stage frames carry the grounding scope and the deadline

`event: stage` frames are P9's own channel and no test outside P9 asserts their
shape. Two additions:

- `{"stage": "grounded", "sections": 7, "facts": {...}}`, where `facts` is
  copied from the composed context and never computed: `channel`, `date_from`,
  `date_to`, `dates`, `breaks`, `plan_status`. When the context reports no
  operator channel the count is withheld and `scope_reason` carries the reason
  instead, because a count over every channel in the file is not the operator's
  count.
- `{"stage": "deadline", "note": ...}` when the run stopped at its own time
  limit. The non-streaming path already carries the same fact in `error`.
- `{"stage": "verifying", "note": ...}`, added in round 5, when the draft answer
  claimed a recorded proposal that the tool record does not carry and the run is
  spending one more turn on it. The dock treats it, and any `thinking` frame, as
  the start of a new turn and clears the text the previous turn painted, so a
  false claim is never on screen beside the sentence that replaces it.

### 2.3 A settings proposal that would move a licence limit carries its permission

On the proposal item, beside `effect` and `diff`:

```json
"permission": {"fields": ["max_breaks_per_hour"], "may_change": true,
               "effective_date": "2026-06-14", "basis_he": "...", "basis_en": "...",
               "record_he": "...", "record_en": "...", "reason": "..."}
```

`may_change` and `reason` come from `guardrail_store.GUARDRAIL_WALL`, so Kai and
the surface that owns the limits cannot disagree. **It discloses and does not
refuse**, for the reason in section 5.

## 5. One thing deliberately not done, with its reason

**Kai does not refuse a licence-limit proposal, it discloses one.** The four
regulatory values still live on `KairosSettings` and `PUT /api/settings` still
carries no guard, so an operator changes them on the settings surface today. A
refusal in Kai alone would make the assistant stricter than the control beside
it, which is the "two different answers in one product" defect this rebuild
exists to remove, and it would regress a capability a passing test asserts
(`tests/test_assistant_actions.py::test_full_server_walls_viewer_and_admits_operator`
applies `max_breaks_per_hour` as an operator and expects 200).

`assistant_permissions.refusal()` is written and tested and turns the disclosure
into a refusal in one call, the day the piece that owns Rules moves the four
fields behind the guardrail store's permission. **That is a handover to P5, not
an open question**: when P5 lands the guard, this line is wired and the test
above becomes P5's to reconcile with C2.
