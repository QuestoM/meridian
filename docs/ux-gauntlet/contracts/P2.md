# P2 Plan, the week: the published contract

The section 8.8 publication for P2: the endpoints it owns, the payload shapes it
emits, the files from section 8.2 it writes, and the helper module names it
creates. It also carries the two things another piece needs from it, the route
map for the four surviving navigation entries and the read-only dependencies
this piece takes on other pieces, so nobody has to read the code to find them.

The destination serves JS-2, the planner, and JS-13, the revenue and yield
owner. Its reference bars are Linear for keyboard control and the command
palette, and Google Ads for how a goal and its progress read together.

## 2. Payload shapes this piece emits

Three payloads changed or are new. The rest are unchanged from wave zero.

### 2.1 `GET /api/schedule`, two added keys

`break_schedule_total_rows` and `scope`. `scope` carries the boundary
disclosure per source, `{plan: note, programmes: note}`, each note being
`channel_scope.scope_note`: `scope_channel`, `scoped`, `rows_in`, `rows_out`,
`channels_in`, `competitor_rows_excluded`, `competitor_channels_excluded`,
`reason`. Measured live with `operator_channel = רשת 13`: 8,704 rows in, 2,540
out, 6,164 competitor rows excluded, 3 competitor channels excluded, and no
rival channel name anywhere in the body.

### 2.2 `POST /api/scenario-compare`, the net, the levers and the week

Each leg gains `levers` (the resolved set it actually ran under),
`money_available`, and, when available, `gross`, `retention_cost` and
`revenue_net`. The top level gains `money_available`, `money_reason`,
`money_basis`, `objective_mode` on each leg, `sameness` and `scope`. The request
gains optional `a` and `b` lever objects; `weight_a` and `weight_b` stay
required, so a caller that already sends the old shape is unchanged.

`objective` keeps its own name and is never relabelled as a net. The net is the
engine's own subtraction through `plan_read_frontier.scenario_plan_money`.

**The window is the plan's own week and the request says so.** `scope` is a new
request field, `week` by default and `day` on request. At week scope each leg is
a real optimizer run per broadcast date, and the response gains:

- `scope`: `{mode, channel, day, dates, date_from, date_to, n_dates, basis,
  days_priced, segments, runs: {total, computed, reused}, elapsed_ms,
  day_reason}`. `mode` is `week` or `day`, and `day_reason` carries why a week
  was not available when a caller asked for one and got a day.
- `by_day`: one row per date, `{date, weekday, a, b, delta_revenue_net}`, each
  leg's row carrying `available`, `reason`, `revenue`, `retention`, `breaks`,
  `money_available`, `gross`, `retention_cost`, `revenue_net`. `null` at day
  scope.
- Each leg gains `days`, `days_expected`, `days_missing`, `objective_basis`
  (`mean_of_days`, because the blended score is normalised inside one day and is
  never summed) and `days_breaching`.

The week is priced only when every date in the window ran and priced. A money
total that silently drops a day reads as the week and is not, so a missing day
makes `money_available` false and names itself in `money_reason`.

### 2.4 `POST /api/scenario-compare/stream`, new

Server-sent events, `text/event-stream`. `window` once, then one `day` per
finished broadcast date `{kind, index, of, day, elapsed_ms}`, then one `final`
frame carrying the identical body the plain route returns. `error` replaces the
rest when the week cannot be resolved or a run fails, and it carries the reason
and no figure.

### 2.3 `GET /api/plan-progress`, new

```json
{"available": true, "channel": "...", "metric": "projected_revenue",
 "currency": "ILS",
 "window": {"date_from", "date_to", "n_dates", "basis", "is_plan_week"},
 "projected": {"revenue", "breaks", "ad_seconds", "average_retention", "retention_basis"},
 "scope": {"scope_channel", "n_channels_total", "plan_date_from", "plan_date_to", "plan_n_dates"},
 "target": {"state", "amount_ils", "at_risk_band_percent", "set_by", "set_at", "note"},
 "verdict": {"state", "reason", "variance_ils", "variance_percent", "threshold_en", "threshold_he"},
 "other_windows": [], "supply": {"door", "route"}, "can_edit": true}
```

`verdict.state` is one of `on_plan`, `at_risk`, `behind`, `unavailable`.
`unavailable` is not a verdict: it is the honest answer when no target exists
for the window, and it carries `reason` and no number.

## 6. Raised, not fixed

Four things measured while building this piece, each on a path this piece does
not own.

1. **`PUT /api/settings` clears every field a body omits, and one of them is the
   competitor boundary.** Reproduced on the running app: a body carrying one
   lever cleared `operator_channel` from `רשת 13` to the empty string and
   `pricing_overrides` from its saved value to `{}`. With no operator channel
   the product's own money restates from ₪10,123,070.80 for the week to
   ₪54,650,165.39, which is the whole four-channel market quoted as the
   operator's. **Owner: P5**, which C2's wave-zero finding 1 already names for
   the settings path. P2's own save sends the full model and refuses to report
   success if the channel moved, pinned by `tests/test_p2_objective_save.py`.
2. **The shell's staleness banner still uses a retired word.**
   `src/shell/ScheduleStalenessBanner.jsx` renders "Recompute now" and
   "Recompute to refresh the schedule, reports, and break plan" above every
   workspace including this one, so section 4.2's verb test fails on this
   surface through a file it does not own. `src/shell/**` is frozen after wave
   zero. **Escalation to the lead**, with `shell/plan-actions.js` at 25
   occurrences and `shell/TVBreakDashboard.jsx` at 13 as the rest of the same
   sweep.
3. **`GET /api/export/schedule.csv` serves every channel.** It downloads all
   8,704 plan rows, of which 6,164 are competitors'. That is the Bar 3 floor and
   it still holds, so nothing is changed, but this piece deliberately does not
   put that download on an operator surface. **Owner: P6**, which owns
   `exporters.py`.
4. **The two prop names `onRecompute` and `recomputeState` survive** in
   `BoardPanel.jsx` because they are the public props of `ScheduleEditor`, which
   is P3's. Renaming them is P3's to do and they are code, not copy.
5. **`tests/test_api_surface_qa.py::test_every_get_endpoint_is_healthy` is red on
   two routes that are not this piece's.** Measured:
   `/api/constraints/restrictions/airings` answers 400 without a title and
   `/api/history/since` answers 422 without a day, so a sweep that calls every
   GET with no arguments now fails. **Owners: P5 and P8.** `/api/plan-progress`
   passes the same sweep, which is why it takes both window bounds as optional.

## 7. Test-change requests to C2

Filed under section 8.2 point 4. Neither file was edited by this piece. Both
tests assert behaviour this specification declares fixed, and in both cases the
production change is the fix rather than the defect.

### 7.1 `tests/test_qa2_api_seams.py::test_schedule_payload_discloses_total_rows_beside_the_display_slice`

1. **The test path.** `tests/test_qa2_api_seams.py:286`.
2. **The assertion that must change.** `body["break_schedule_total_rows"] == total`,
   where `total` is the row count of `output/weekly_break_schedule.csv`, 8,704.
   It now reads 2,540.
3. **The production change that forces it.** Section 8.3 of the specification
   names P2 as the piece that applies the competitor boundary to
   `/api/schedule`, and W0-4 measured the breach it closes: the 200-row display
   slice held 96 rows of one rival, 73 of a second and 28 of a third, against 3
   of the operator's own. The payload is now scoped, so its total rows are the
   operator's 2,540 and the disclosure of what was dropped travels with it under
   `scope`, which is where 8,704 is still reported as `rows_in`.
4. **Which of the two is wrong.** The test. Its own subject, that a display
   slice must disclose the size of the set it came from, is preserved and is
   stronger: the payload now reports the size in, the size out, the number of
   competitor rows excluded and the number of competitor channels excluded. The
   figure it pins is the pre-boundary one.

### 7.2 `tests/test_insights_endpoints.py::test_scenario_compare_runs_two_real_optimizations`

1. **The test path.** `tests/test_insights_endpoints.py:128`.
2. **The assertion that must change.** `body["delta"]["revenue_net"] is None`.
   It now reads a real figure, measured 1,273,470.40 net against 1,414,695.20
   gross and 141,224.80 of retention cost on `רשת 13 / 2024-11-11`.
3. **The production change that forces it.** JS-2's done condition is a
   comparison on revenue net of retention cost, and the baseline recorded the
   panel printing "Net after retention cost: Not exposed" as a complete failure
   of the story. The subtraction is computed by the frozen read layer's own
   pricer, `plan_read_frontier.scenario_plan_money`, on the same per-break basis
   the committed plan's yield-per-second money uses.
4. **Which of the two is wrong.** The test. It pins the absence the job story is
   defined against. The honest half of its assertion survives and is worth
   keeping in whatever replaces it: when the scenario plan and the rebuilt
   segments no longer join, the pricer refuses, `money_available` is false and
   the reason is carried verbatim rather than replaced by a zero.
5. **What it costs now.** Every other assertion in that test still passes at week
   scope, including the one that matters most to it, that revenue-first places at
   least as many breaks as retention-first: measured over the plan's seven days,
   weight 0 places 0 breaks and weight 100 places 553. The test itself is slower,
   14.5 s for the two tests in that file against roughly 2.5 s before, because
   the route now runs the week. A caller that wants the old speed passes
   `scope: "day"`.

## 8. What the week costs, measured

Recorded 2026-08-01 against this tree, `operator_channel = רשת 13`, plan week
2024-11-01 to 2024-11-07, basis `plan_first_week`.

| Measurement | Figure |
|---|---|
| One leg on one broadcast day, refined optimum | 0.69 to 1.30 s |
| Two legs over the plan's seven days, cold | 11.1 s server side, 11.2 s in the browser from click to both cards |
| First comparable broadcast day on screen | 1.9 s |
| One leg unchanged, the other moved | 7.0 s, and the payload reports 7 computed and 7 reused |
| Both legs already run this session | 0.01 s, and the payload reports 0 computed and 14 reused |
| The single representative day, `scope: "day"` | 2.5 s |
| The baseline this replaces, one day | 20.35 to 25.62 s (`06-baseline.md:146`) |

JS-2's bar for this step is 5 s and the week is over it. That is stated on the
surface rather than hidden: the panel prints the run count, the clock and how
many runs were reused, and the days arrive one at a time so the wait is legible
work rather than a spinner. The greedy optimum would fit the bar at 0.36 s a day
and is refused: measured on `רשת 13 / 2024-11-04` it reports 1,555,641.19 where
the refined optimum the saved plan is built with reports 1,698,547.39, so it
would compare two plans the operator would never run.
