# W0-5, the evaluation seam and the cache

The piece's first deliverable is an attribution, not a fix, because two of the
three premises the latency bars were built on turn out to be wrong. This
document is the attribution first, then the contract for the three modules the
piece publishes and freezes under section 8.8.

Everything below was measured this session with `~/.venvs/meridian/bin/python`
on `רשת 13` / 2024-11-01, 82 segments, 80 breaks, against my own instance on
port 8025 started from the repo root. Every number is reproducible with the
commands named beside it.

## 2. What the attribution overturns

**The double optimize is the cost, not a rounding error.** Section 8.4 says two
legs are 1.8 s of a 19.77 s response, so 9 percent. Measured on an idle process
the two legs are 1.81 s of an 1.83 s response, so **99 percent**. Dropping one
leg is not a 5 percent saving; it halves the response. That is the single lever
on both endpoints.

**The 6.38 s of "cold segment construction" is module import, not construction.**
In a fresh process the first `preview_inputs` call takes 6.118 s and imports
**5,212 modules** inside itself, including arviz, scipy, sklearn and xarray. Time
those imports separately and the picture is unambiguous:

| | Measured |
|---|---|
| `from kairos.model.impact import load_impact_model` | **3.447 s** |
| `from kairos.service import ...` | 0.013 s |
| loaders, transform, pricing, core | 0.002 s |
| the first real call once the imports are paid | **0.381 s** |
| the second call | 0.013 s |

So the cacheable part of the cold cost is 0.38 s, not 6.38 s, and the 3.4 s
above it is a one-time process cost that no cache can remove. In the server it
is not even paid by a request: uvicorn imports the app at boot, which is why the
port opens 5.94 s after launch and why the first request on my instance was
2.744 s rather than 8 s.

**The missing 13 seconds is contention, not a hidden stage.** The request's own
work is fully accounted for above, so the gap has to be time the process spent
not running this request. Two mechanisms, both measured:

| Concurrent identical requests | Latency each |
|---|---|
| 1 | 1.834 s |
| 2 | 3.294 s mean |
| 3 | 6.345 s mean |
| 4 | 7.252 s mean |
| 6 | 9.724 s mean |

The route is CPU-bound pure Python, so N simultaneous requests share one GIL and
each one's latency scales with N. A 19.77 s response is what this curve gives at
roughly ten to eleven concurrent units of the same work.

The second mechanism is the startup warm-up. `server.py:284` starts a thread
that runs overview, forecasts, campaigns and inventory, then two frontier sweeps
in threads of their own. Sampling the scoped request from boot:

```
t+  5.9 s  2.500 s     t+ 22.0 s  4.916 s     t+ 39.8 s  1.637 s
t+  8.9 s  2.300 s     t+ 27.4 s  3.301 s     t+ 45.5 s  1.868 s
t+ 14.4 s  3.710 s     t+ 31.2 s  3.640 s     t+ 49.1 s  2.007 s
t+ 18.7 s  2.844 s     t+ 35.4 s  1.781 s     t+ 56.8 s  1.748 s
```

For the first 35 seconds of server life the same request costs 2.2 to 4.9 s, and
then it settles at 1.7 to 1.9 s. And a single unscoped preview in the same
process took a scoped request from 1.75 s to **7.70 s** while it ran.

**The unscoped preview is a different animal and should be measured as one.**
`preview_inputs(None, None, None)` builds **8,704 segments across 120
channel-days**, 106 times the scoped work, in 0.170 s. Optimizing that is what
`06-baseline.md` recorded as 55.60 s. It did not finish inside a 900 s client
timeout on this data while sharing the process. Nothing in this piece changes
it; it is recorded so a later bar is not set against it by accident.

**Honest limit.** I could not measure the instance the 19.77 s was taken on: the
long-lived server on port 8000 enforces authentication and I had no credentials,
and the spec does not record that process's state. So this section reproduces
the mechanism with a dose-response curve, not the exact figure.

## 3. What each latency bar now needs

- **JS-3, a money answer inside 500 ms.** Reached, with room. With a prepared
  basis `evaluate.score` is **72 microseconds** for 82 segments, 13,153 times
  cheaper than the 947 ms optimize leg it replaces. Building the basis is 147
  microseconds, and the segments behind it are 12 ms warm. A drag answers in
  well under a millisecond once the day is open.
- **JS-4, a preview inside 3 s.** Reachable without any cache. Warm segments
  0.012 s plus one leg 0.87 s is about 0.9 s of engine work, and the second leg
  is the thing to remove: read the baseline from the saved plan instead of
  recomputing it. Section 8.4 made this bar conditional on the 13 s being closed;
  it is closed, and the condition is discharged. The remaining risk is not the
  work, it is contention, so the honest engineering note for P5 is that a preview
  fired while the warm-up thread or another sweep is running will still miss 3 s.

The diff on the two files it was allowed to touch, and nothing else:

| File | Change |

## 5. `kairos/optimize/evaluate.py`, the scoring seam. Frozen

```python
from kairos.optimize.evaluate import (
    Evaluation,        # NamedTuple(objective, revenue, retention)
    Basis,             # NamedTuple(segments, revenue_scale, total_tvr, derived)
    evaluation_basis,  # (segments, *, risk_lambda=0.0, revenue_scale=None, total_tvr=None)
    score,             # (basis, counts, *, revenue_weight, placements=None) -> Evaluation
    evaluate_day,      # (segments, counts, *, revenue_weight, risk_lambda, placements,
                       #  revenue_scale, total_tvr)
    counts_from_result,
    pins_from_result,
)
```

**Both normalising constants are the caller's to supply, or neither is, and the
arrangement may not be wider than the basis.** This is the second round of the
signature. The first let a caller override `revenue_scale` and gave no way to
supply `total_tvr`, and `score` dropped a count for a segment the basis did not
carry, so the two ways to hold part of a day both produced a confidently wrong
number instead of a refusal. Measured on the real 82-segment channel-day
`רשת 13 / 2024-11-01`, one break in every segment: the whole day scores objective
0.542990 on revenue 1,067,797, its first 41 segments with both constants derived
score 0.542990 on 426,777, which is a scope of its own and honest, and those same
41 carrying the whole day's `revenue_scale` against their own derived `total_tvr`
score 0.445411, which is a whole-day revenue term blended with a half-day
retention term and describes no scope at all. Now: supplying one
constant without the other raises, an arrangement naming a segment outside the
basis raises, a duplicated `segment_id` raises, and `Basis.derived` records which
claim the basis is making. A basis spanning several channel-days is still legal
and still reports the global blend, because the underlying contribution is
additive over groups. Pinned by `tests/test_w0_cleanup_evaluate_basis.py`.

The contract is that the cheap number IS the plan's number. On the real
channel-day, against `_optimize_one_day`'s own reported totals:

| | Optimizer | evaluate | Difference |
|---|---|---|---|
| revenue | 1067845.5490407092 | 1067845.549040709 | -2.33e-10 ILS |
| retention | 0.9476976638937574 | 0.9476976638937574 | exactly 0 |
| objective | 0.5416288266188297 | 0.5416288266188297 | exactly 0 |

To the shekel is met by a factor of four billion. The revenue residue is float
summation order: the optimizer totals in its state-dict order, this seam totals
in segment-id order.

Three details make that identity hold rather than nearly hold, and a consumer
must not reimplement them: the same risk adjustment on the coefficients, the
same default `revenue_scale` and `total_tvr`, and the same segment-id ordering.
Two honest limits: the score is the engine basis, so with the owner-gated
quarter-hour settlement on, the plan's restated revenue differs by construction;
and a score is not a compliance check, so a surface that lets a person move a
break must still run `kairos.optimize.guardrails.evaluate`.

## 6. `kairos_api/read_cache.py`, the shared read cache. Frozen

```python
from kairos_api import read_cache
read_cache.cached(namespace, key, fingerprint, build)
read_cache.file_signature(path) / file_signatures(paths) / directory_signatures(dir, pattern)
read_cache.lookup / store / invalidate / stats / reset_stats / configure
```

A value is served only when its fingerprint compares equal, every namespace is
LRU bounded at eight entries, the build runs outside the lock, and `stats()`
reports hits, misses, stores, evictions and entries so nobody has to guess
whether it is helping. It generalises the three hand-rolled copies already in
the codebase: the `(path, mtime_ns, size)` memo in `kairos/data/loaders.py`, the
`_signature` plus `lru_cache` pair in `kairos_api/core.py`, and the frontier's
warm map.

**It ships wired into `preview_inputs` and switched off, and that is a
measurement, not a hedge.** With the cache on, `preview_inputs` drops from 12.13
ms to 2.40 ms: the cacheable build is 10.75 ms and the fingerprint costs 0.152
ms. On an 1,800 ms response that is a **0.54 percent** saving. Against it stands
a permanent obligation: every future input to segment construction must be
reflected in the fingerprint, or a money number goes stale. Nine milliseconds do
not buy that obligation, so `USE_READ_CACHE = False` and the reason is written
down where the switch is.

The on path is complete and tested, so a later piece with a genuinely expensive
read can flip it after measuring its own path. The fingerprint carries the saved
settings, the live pricing model, the folded assumptions (which is where the
measured first-break multiplier lands, and it is neither a file signature nor a
seam identity), today's date, the signatures of every file under `config/` and
`models/` plus the settings, both programme sources and the events store, and
the seam functions themselves by identity. Three tests hold it: a warm cache
must not survive a changed first-break multiplier, a replaced segment builder,
or a changed settings object.
