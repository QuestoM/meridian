# P5 contract: Rules

The workspace where a rule is written in plain language, states its effect
before it is saved, and carries the permission that decides who may write it.
Published under section 8.8: the endpoints, the files from the section 8.2 row,
and the helper modules created under the `<parent stem>_<role>.py` rule.

It also carries one blocker, filed below with the measurement, because the
strongest permission on this surface can be walked around through a route P5
does not own.

## Blocker: the operator channel can be moved by a route P5 does not own

**Status: closed by the lead on 2026-08-01.** The call landed in
`kairos_api/settings_api.py:56-59`, exactly the patch filed below. Measured
after it, through the real app on real resolved sessions: an operator of either
affiliation is refused `PUT /api/settings` with the channel changed, **403**
`בחירת ערוץ המפעיל שמורה למנהל המערכת`, and the channel on disk does not move;
the same account still saves any other lever through the same route, **200**;
an administrator still moves the channel, **200**. The OpenAPI sweep over every
write operation whose body can carry the field now returns an empty open set,
so `test_no_route_lets_a_non_admin_move_the_operator_channel` lost its strict
`xfail` marker and the file reads 8 passed. The section below is kept as the
record of what was measured and why, not as an open item.

### The measurement

Taken on the real app with real resolved sessions, settings relocated to a
temporary path so no tracked file moved. Two accounts, both with the operator
role so the middleware's read-only rule is not what answers, one on each side of
the affiliation line.

| Act | Channel-affiliated operator | Company operator |
|---|---|---|
| `PUT /api/rules/operator-channel` to a rival channel | **403** `בחירת ערוץ המפעיל שמורה למנהל המערכת` | **403**, same detail |
| `PUT /api/settings` with `operator_channel` changed to the same rival | **200, and the channel moved** | **200, and the channel moved** |

After that write, `GET /api/settings` reports the rival as the operator's own
channel, and every scoped P5 surface follows it: `/api/constraints/options`
returns `scope_channel` set to the rival with `scoped: true`, 2,727 of 8,704
rows kept and 5,977 excluded as competitor rows, and
`/api/constraints/restrictions/titles` returns 40 rival programme titles.

This is not a leak, it is an inversion. The product hides the operator's own
channel and treats a competitor's as owned, and every figure downstream is
computed for the wrong broadcaster while every label still says it is yours.

A second defect sits on the same route and was measured with it: a settings
write whose body leaves `operator_channel` out defaults it to the empty string
and clears the declaration, which un-scopes every figure in the product. P2
measured the same thing from the client side and worked around it in its own
surface (`plan/week/use-plan-surface.js:142-160`); this is the server-side fix
for it.

### Why P5 cannot close it

`kairos_api/settings_api.py` is on W0-4's row in the section 8.2 ownership
table and appears on no wave-one row, so it is frozen to every wave-one builder.
The two other paths that could carry the rule, `kairos_api/core.py`
(`_save_settings`, `KairosSettings`) and the region of `kairos_api/server.py`
above the append marker, are frozen for the same reason. The append region below
the marker cannot help either: the OpenAPI bar on an append forbids redefining a
path, and FastAPI matches the first registered route, so a later mount would not
shadow the existing one even if it were allowed.

### The exact patch

In `kairos_api/settings_api.py`, in `update_settings`, two added lines:

```python
@router.put("/api/settings")
def update_settings(settings: KairosSettings, request: Request = None) -> dict[str, Any]:
    from kairos_api import version_store
    from kairos_api.compliance_api_licence import guard_channel_move

    guard_channel_move(settings, request)
    version_store.snapshot_manual_edit(request, "settings")
    return _model_dump(_save_settings(settings))
```

`guard_channel_move` is at `kairos_api/compliance_api_licence.py:87`. It uses
the same `CHANNEL_WALL` and the same schedule validation as
`PUT /api/rules/operator-channel`, so the two enforcement points are one rule
and not two that can drift. It returns immediately when the write does not move
the channel, which is the path every shipped client takes, because both of them
send the settings model whole. The import is inside the function because that
is how this package's cross-module calls are written and it cannot create a
cycle at import time.

### The proof the patch closes it, and closes nothing else

Measured by applying exactly those two lines to a copy of the module, loading it
and swapping its four routes into the real app in memory, then re-running the
probes:

| Act, after the patch | Result |
|---|---|
| Either non-admin moves the channel through `PUT /api/settings` | **403** `בחירת ערוץ המפעיל שמורה למנהל המערכת`, channel unchanged |
| An administrator sends a body that omits `operator_channel` | **400** naming the field and the route that moves it, channel unchanged |
| An administrator moves the channel explicitly | **200**, channel moved, which is the capability that exists today and Bar 3 protects |
| An administrator names a channel the schedule does not carry | **400** `'Channel 9' is not a channel in the loaded schedule. Load its programmes first.` |
| A non-admin saves the whole settings model with a lever changed and the channel unchanged | **200**, `revenue_weight` 65 saved, channel intact |

### The test that makes it visible, and retires itself

`tests/test_p5_channel_declaration.py`. It does not name one route. It reads the
running app's own OpenAPI document, finds every write operation whose declared
body can carry `operator_channel`, sends each one a body that carries it as a
non-admin from both sides of the line, and asserts the channel on disk did not
move. A route added later that can carry the field is swept in without anyone
remembering to add it.

Measured today: the sweep finds exactly two routes,
`PUT /api/rules/operator-channel` and `PUT /api/settings`, out of 88 write
operations on 146 paths.

- `test_no_route_lets_a_non_admin_move_the_operator_channel` is the bar. It was
  marked `xfail(strict=True)` with this blocker as its reason, so pytest printed
  the reason in the run summary. Strict meant that the day the two lines landed
  it reported `XPASS(strict)` and failed, which was the instruction to delete
  the marker, so the blocker could not outlive its cause. Verified all three
  ways: 7 passed and 1 xfailed while it was open, 7 passed and 1 failed with the
  patch applied to a copy, 8 passed with the patch shipped and the marker gone.
  It is also the permanent catch, because a writer added later that can carry
  the field is swept in and has to answer the same way.
- `test_the_route_that_was_open_refuses_the_move_and_still_saves_the_rest` pins
  the route by name, because the sweep above is derived from the OpenAPI
  document and would still pass if the route stopped accepting settings at all.
  It asserts the three answers together: the refusal with the declaration
  route's own words, the administrator's move still landing, and a non-admin
  still saving every other lever, which is the capability a blunter guard would
  have taken away.

## The condition builder's value picker, and the boundary it was open on

The composer's programme picker was scoped to the operator's own channel from
the day it shipped, and asserted by
`test_the_title_picker_only_offers_the_operator_own_channel`. The condition
builder beside it read a second, older option route, and that one was never
scoped. Measured on the reference EPG with the operator channel set to
`רשת 13`: `GET /api/constraints/options` served **418 programme titles, of which
106 are the operator's own and 312 are three rivals' entire lineups** (149, 104
and 59), plus all four channel names. So the surface that authors a restriction
offered a representative three competitors' schedules.

`_constraint_options.operator_scope_options` now builds the programme, genre and
channel lists through the frozen `kairos_api.channel_scope`, and `scope_options`
serves them. Measured on the running app after the change: **106 titles, 0 of
them rival, 0 of the operator's own lost, `channels` and `available_channels`
both `["רשת 13"]`, and zero rival channel names anywhere in the payload**, with
the scope note disclosing 8,704 rows in, 2,540 out, 6,164 competitor rows and 3
competitor channels excluded. The composer's 40 titles are a subset of the
builder's 106, so the two pickers on this surface now agree about whose
programme is whose.

With no channel declared the scope cannot be applied, so the lists are empty and
carry the reason and `PUT /api/rules/operator-channel` as the route that
supplies the missing input. The pass-through form of `scope_frame`, which
returns the whole market with a note, is deliberately not served here: passing
the market through is the exact breach this closes. `ConstraintBuilder.jsx`
prints the scope note above the picker either way.

`tests/test_p5_constraint_options.py`, 6 tests, derives the rival set from the
reference EPG rather than from a fixed list, so it keeps holding when the data
changes.

## The other handover item on this path, and why it is not closed here

Wave zero's handover asks whoever owns the settings path to stop a `GET` from
rewriting `data/kairos_settings.json`. The sweep has now been run and **no read
in it writes**, so there is nothing here for P5 to fix and the handover item
should be re-aimed rather than assigned.

The measurement, with the document relocated to a temporary copy so no tracked
file moved: every argument-free `GET` the running app publishes, **74 of the 76**
(`/api/constraints/effect` and `/api/overrides/effect` excluded, both run the
optimizer and neither is a candidate), called in turn against the real app.
**None of them rewrote the document.** Tracked by inode rather than by content
hash, deliberately: a load-modify-save that writes the same bytes back is still
a write and a content hash cannot see it, while the store writes atomically with
`os.replace`, so the inode moves on every write whatever the bytes are. Both
forms of the sweep answer the same, and the first request through the client is
what runs the startup handlers, so startup is inside the measurement.

The static half agrees. Outside `settings_api.py` the product holds three calls
to `_save_settings`, at `compliance_api_licence.py:201` and `:334` and
`model_activation.py:117`. The second and third are the bodies of
`PUT /api/rules/operator-channel` and the activation write. The first is
`_write_through_if_due`, reached only from `POST /api/rules/guardrails` and
`POST /api/rules/guardrails/apply`, and it returns before writing when the
limits in force already equal the engine's, which is the state on disk today.

So the diff C2 saw came from a write, not from a read. What remains true, and is
the part worth acting on, is C2's own conclusion rather than its diagnosis: a
store the running product writes is checked into git, so it will keep producing
diff noise a gate has to classify by hand. That is a decision about whether the
file is tracked, and it belongs to the lead.
