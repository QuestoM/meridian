## 2. Round six: the client the name space never learned about

### 2.1 The defect, measured

Two stores describe a client. `data/agency_advertisers.csv` says which agency it
buys through; `data/advertiser_names.csv` says who it is. Only the first of the
two had a creation path.

Measured on the working tree at the start of round six: the link store held 45
advertisers, the name space held 41, and the four in the difference were exactly
the clients the onboarding flow had created. Two consequences followed.

- **The suite.** `tests/test_w0_3_advertiser_identity.py:127` asserts the two
  sets are equal, so the tree shipped red.
- **The screen.** A created client resolved to no record at all, so
  `sourceLabel` printed `מקור לא ידוע` for ever and no pricing rule could ever
  be bound to it by name. The product's own creation path produced a
  second-class client.

### 2.2 The fix, at the chokepoint rather than at the flow

The critic named `campaigns_api_onboarding.py`, which is where the flagship flow
lives. The flow reaches the link store through `create_link`, and so does the
standalone link control on the Agencies surface, so the naming was put on the
link itself and both writers inherit it.

- `kairos_api/agency_conditions_identity.py` is new. `register_advertiser_name`
  appends one row to the name space with `source = "manual"` and `first_seen`
  set to the date of creation, under the module lock, with a timestamped backup
  and a temp file plus `os.replace`, which is the store discipline every sibling
  here already uses. It is idempotent under the same fold `resolve_advertiser`
  uses, so a name already held is left exactly as it is.
- `kairos_api/agency_conditions.py::create_link` calls it after the link row
  lands and returns the outcome on the response.
- `kairos_api/campaigns_api_onboarding.py::_link_advertiser` returns that
  outcome, and names the client on the already-linked path too, so a client
  linked before this existed becomes a named record the next time an order is
  booked for it. It does so only when the link is manual: an observed link came
  from a daily file, and writing `manual` over it would misstate where the name
  came from.
- The name space is found beside the link store rather than through a second
  constant, so a caller that redirects its stores, which is every test in this
  suite, redirects this one with them and never writes a name into the
  operator's real data.
- `OnboardClientFlow.jsx` states the outcome on the confirmation, in the two
  words it can honestly say: named now, or already a named client.

**Nothing is invented.** The row carries the string the operator typed and
nothing else: no display name, no alias, no premium, no money. `source` is
`manual` because nothing observed this client, and that word is what tells every
reader which figures can exist for it at all.

### 2.3 What it moved, and what it did not

Measured from the seed at `HEAD` with this code in place, before any use of the
flow: 41 names, 41 links, and all four assertions of
`test_the_name_space_holds_exactly_what_was_observed` hold. **On the shipped
seed the change is a no-op.** It only ever writes when somebody creates a
client.

Measured after booking one client through `POST /api/clients/onboarding` on that
same seed: 42 names, 42 links, `:127 names == linked` **true**, which is the
assertion that was false before this change, and `:126 names == observed` and
`:128 all source observed` now false. That is the subject of the request below.

## 3. The test-change request, to C2, under section 8.2 rule 4

**Open, awaiting a ruling.** No test file was edited. The four things rule 4
asks for.

### 1. The test path

`tests/test_w0_3_advertiser_identity.py`, at
`test_the_name_space_holds_exactly_what_was_observed`. The file has no owner
under rule 2: it imports `kairos.optimize.advertiser_rules_identity` and
`kairos_api.advertisers_identity`, which are W0-3's and frozen at wave-zero
close, so P4 may not edit it.

### 2. The assertion that must change

**Line 128**, `assert all(record.source == "observed" for record in
names.values())`. It requires every row of the name space to have been observed
in a daily file, which is false for a client an account manager created ten
seconds ago and true only of a store nothing writes.

**And, entailed by the same one production change, line 126**,
`assert set(names) == observed`. A created client is in the name space and is
not in the daily file, so the two sets differ by exactly the clients this
operator has booked. Rule 4 asks for the assertion at stake; naming one and
leaving its twin to surface later would be filing half a request.

Lines 127 and 129 must survive unchanged. Line 127 is the invariant this round
exists to restore, and line 129 holds because a created client carries the date
it was created.

### 3. The production change that forces it

`kairos_api/agency_conditions_identity.py::register_advertiser_name`, called
from `kairos_api/agency_conditions.py::create_link` and reported through
`kairos_api/campaigns_api_onboarding.py::_link_advertiser`. It writes one row
with `source = "manual"`.

Measured, on the seed at `HEAD`, one booking through the real router stack:

| Assertion | Before the booking | After it |
|---|---|---|
| `:126 set(names) == observed` | true | **false** |
| `:127 set(names) == linked` | true | true |
| `:128 all source == observed` | true | **false** |
| `:129 all first_seen` | true | true |

Without the change, the same booking leaves `:127` false, which is the state the
tree shipped in.

### 4. Which of the two P4 believes is wrong

**The test.** Its premise is that the name space holds exactly what a daily file
was observed to hold, and that premise was true only while nothing could create
an advertiser. Section 5.5 of the specification and the owner's ruling of
2026-08-01 both put a creation path in front of it: identity is re-keyed on the
observed names, and the account manager creates clients. The name space's own
module says so in its docstring, that a record exists "so an advertiser can be a
named record before anybody has written a rule for it", and the migration
already keeps a hand-added name with the source it carries rather than dropping
it.

**The suggested edit, which is C2's to make or refuse.** Scope both assertions
to the observed rows, and assert the created rows are marked rather than absent:

```python
observed_rows = {key: record for key, record in names.items() if record.source == "observed"}
assert set(observed_rows) == observed
assert set(names) == linked
assert all(record.source in {"observed", "manual"} for record in names.values())
assert all(record.first_seen for record in names.values())
```

That keeps every property the test was written to protect, including the one it
protects best, which is that nothing invents a name, and it stops asserting that
the product has no creation path.

## 4. Round six: the rollup panel read zero while it was still reading

`CampaignRollupPanel` had two states where the data has three. The round-five
critic measured the header saying "0 קמפיינים" over "לא נמצאו שורות קמפיינים" at
1,883 ms with the read delayed, and for 132 to 277 ms warm.

**Where the zero really came from.** Not from the panel's own read. The shell
seeds its shared state with `fallbackCampaigns` at `use-kairos-data.js:22` and
passes it down, and it hands the same object back when the shared read fails
(`use-kairos-data.js:55`). That placeholder is truthy and holds an empty list,
so the panel's own read never ran and `campaigns || fetched || { campaigns: [] }`
printed the placeholder's empty list as a measured count. Truthiness cannot tell
a placeholder from a payload; identity can, and `fallbacks.js` is on W0-2's
read-only shared surface, so the panel compares against the object itself.

The panel now has four states: the shell's payload used as it is, a read of its
own in flight, that read landed, and that read failed. The honest empty state
survives untouched: a real zero still says zero and still says no rows were
found.

**Measured in a browser on port 8034,** with `/api/campaigns` rejected at
1,500 ms and a mutation observer recording every distinct state of the panel:

| At | Header | Table |
|---|---|---|
| 1,675 ms | loading | Loading campaigns seen in the source data |
| 1,708 ms | not loaded | The campaign rollup could not be read, so no count is shown rather than a zero |

The strings `0 campaigns` and `No campaign rows were found` appear at no point.
On the healthy path the same observer records one state, `50 campaigns` with its
rows, first painted at 2,081 ms.

`tests/test_p4_rollup_tristate.py` executes the shipped component through all
six sequences on the JSX compiler the product builds with, and its last test
puts the defect back from `HEAD`, which claims zero in both the panel's own read
and the placeholder sequence. Seven tests, all passing.

## 5. A finding for the lead, which is not a request

Three further assertions are red on the working tree and **none of them is
forced by anything P4 changed**. They are red because a critic's browser runs
wrote four agencies, four links and four campaigns into stores that are tracked
in git, and three tests pin those stores as if they were seed files.

- `tests/test_qa6_agencies.py:301`, `set(frame["name"]) == SEED_AGENCY_NAMES`
  and `len(frame) == 9` and `(frame["data_source"] == "synthetic").all()`.
- `tests/test_qa6_agencies.py:313`, `(links["source"] == "observed").all()`.
- `tests/test_w0_3_advertiser_identity.py:391`, `written ==
  set(_daily_advertisers())`, which fails because
  `scripts/migrate_advertiser_identity.py::observed_advertisers` reads the real
  link store and the test redirects only three of its four paths.

Measured with the three stores taken from `HEAD` into a temporary directory and
the current code: 9 agency rows all synthetic, 41 link rows all observed, the
name space equal to both the daily file and the link set, and the migration
writing exactly the daily advertisers with `source = observed` and a date. **All
four assertions hold on the seed.**

So the defect these three describe is real but it is not a test defect and not
P4's change: `POST /api/agencies` and `POST /api/agencies/{id}/advertisers`
predate wave one, an agency deactivates rather than deletes by P4's own Bar 3
row, and there is therefore no product act that can return `data/agencies.csv`
to nine rows once a tenth agency exists. A test that pins a live store to its
seed goes red the first time anybody uses the product, which is the same class
of finding as the settings store that rewrites itself on a read. P4 does not
open a request on these because P4 did not force them, and it does not hand-edit
the stores because they are not on its row. They are recorded here so the ruling
that covers section 3 can cover them in the same pass if C2 chooses.
