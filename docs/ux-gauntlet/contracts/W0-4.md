# W0-4 contract: the wall and the words

Five cross-cutting rules, each one importable module, each adopted in one line.
Published and frozen under section 8.8. Nothing in this piece changes what a
person sees or a number anyone reads; the modules exist and are tested, and the
routes that will use them belong to their owners.

## Rule 1: the affiliation wall and the `can_edit` contract

`kairos_api/affiliation_wall.py`. One `Wall` declares a surface's permission
rule once and serves it three ways.

```python
from kairos_api.affiliation_wall import Wall

MODEL_WALL = Wall(detail="התצוגה הזו שמורה לצוות החברה", company_only=True)
```

| Use | Call | Effect |
|---|---|---|
| Gate a whole route, read and write | `@MODEL_WALL.guard()` under the route decorator | 403 with the detail before the handler runs |
| Gate one branch | `MODEL_WALL.require(request)` | raises `HTTPException(403, detail)` |
| Tell the truth before the click | `MODEL_WALL.stamp(body, request)` | writes `can_edit`, and `can_edit_reason` only when false |
| Ask | `MODEL_WALL.allows(request)`, `MODEL_WALL.reason(request)` | bool, and the detail or None |

`Wall(detail, company_only=True, roles=WRITE_ROLES, role_detail=...)`.
Affiliation is the outer gate and role the inner one, so the reason names the
gate that actually closed: a channel administrator is refused on affiliation, a
company viewer on role. `roles=frozenset()` gates visibility only.
`company_only(detail)` is the one-line form of a read-and-write company wall.

`session_for(request)` returns `{username, role, affiliation}` or None.
`is_company(request)` and `require_company(request, detail)` delegate to
`events_access`, so there is exactly one implementation of the affiliation
question in the process and the five shipped `require_company_editor` call
sites are untouched.

**Unknown identity is permitted**, exactly as the events guard already behaves:
auth disabled, no request object, or no resolvable session all read as company
and as permitted. The server middleware answers 401 before any route runs, so
this is not a hole, and it is what keeps a deployment without login open.

**The decorator keeps FastAPI's injection working.** A route that declares
`request: Request` is called unchanged. A route that declares none gets one
appended to the signature FastAPI reads and stripped before the handler is
called. Postponed annotations are handled, which matters because most modules
here use `from __future__ import annotations` and the annotation is the string
`"Request"` at runtime.

**The four open doors this closes**, when their owners adopt it:
`GET /api/impact` and `GET /api/model/audience` are P7's, `GET /api/parameters`
is W0-4's remaining work, and `/api/events`'s `model_context` is P5's.

## Rule 2: the competitor boundary

`kairos_api/channel_scope.py`. The operator owns exactly one channel, read from
`settings.operator_channel`.

```python
from kairos_api import channel_scope

rows, scope = channel_scope.scope_records(rows)          # payload records
frame, scope = channel_scope.scope_frame(frame)          # a pandas frame
```

Both return `(data, note)`. The note is the disclosure that travels with the
payload: `scope_channel`, `scoped`, `rows_in`, `rows_out`, `channels_in`,
`competitor_rows_excluded`, `competitor_channels_excluded`, `reason`. With no
configured channel the data passes through unchanged and `reason` says why, so
a surface that cannot scope says so rather than quietly serving the market
total as the operator's.

`competitor_aggregate(records, sum_fields=(...))` is the only shape in which a
competitor may reach a payload: `{channels, rows, totals}`, no name, no
per-channel breakdown, no ranking. It exists because the retention model
genuinely needs the lineup as a factor.

**The measured breach, on the reference data with `operator_channel = רשת 13`,
taken from the live instance before this module existed.** `GET /api/schedule`
serves `break_schedule` as `head(200)` of the plan: 96 `קשת 12`, 73 `כאן 11`,
28 `עכשיו 14`, and 3 of the operator's own. Its `rows` canvas carries 1,852
programmes across four channels, of which 1,328 are competitors'. Its nested
`break_operations` carries 12 programmes per channel. `GET /api/break-operations`
carries 12 programmes for each of the four channels, 48 in total.

**Who applies it.** P2 on `/api/schedule`, P3 on `/api/break-operations`, P9 on
Kai's context. C1 verifies. This piece does not edit those routes.

## Rule 3: the vocabulary

`tv-break-dashboard/src/vocabulary.js`, dependency-free so any tree can import
it.

```js
import { word, genreLabel, pricingClassLabel } from '../vocabulary.js';

word('object.break', locale);        // ברייק / break
word('action.run_plan', locale);     // הריצו את התוכנית / Run the plan
```

72 concepts, each with exactly one English and one Hebrew word, namespaced
`activity.`, `action.`, `place.`, `object.`, `concept.`, `state.`, `role.`,
`affiliation.`. An unknown key returns an empty string, so a missing word is a
gap a reviewer notices rather than a token a person has to decode.

**The retired words are absent from the file**, not commented out and not kept
as aliases. The critic's grep for recompute, rebuild, חישוב מחדש and
בנייה מחדש under `tv-break-dashboard/src/` returned 159 hits before this wave;
zero of them are in this file, and a test in
`tests/test_w0_4_vocabulary.py` fails if one appears.

**The two value sets that used to share a name.** Measured:
`output/weekly_break_schedule.csv` carries 15 distinct `program_type` values,
while `config/optimization_weights.yaml` and `models/tv_break_coefficients.json`
price and measure on 4. They share only `News` and `Other`. So there are two
concepts, not one with four names:

- `concept.programme_genre`, values in `PROGRAMME_GENRES`, 15 members, read
  with `genreLabel(value, locale)`. This is what a scheduler reads.
- `concept.pricing_class`, values in `PRICING_CLASSES`, 4 members, read with
  `pricingClassLabel(value, locale)`. This is what the rate card and the
  retention model use.

A test compares both lists against those files, so a value set cannot drift
from the file that produces it.

## Rule 4: the session

`tv-break-dashboard/src/session.js`, dependency-free for the same reason.

```js
import { fetchSession, payloadCanEdit, doorFor, WALLS } from '../session.js';

const { session } = await fetchSession();
const { canEdit, reason } = payloadCanEdit(payload, session, WALLS.events);
```

`normalizeSession(body)` turns `GET /api/auth/me` into
`{authDisabled, username, displayName, role, affiliation, job,
mustChangePassword, isCompany, isAdmin, canWrite}`. Login not set up is an
honest state of its own, not a fake identity, and every gate reads open, which
is what the server does.

**The endpoint is the authority.** `payloadCanEdit(payload, session, wall)`
uses the payload's own `can_edit` and its reason verbatim whenever the payload
carries one, and falls back to `sessionCanEdit(session, wall)` only for an
endpoint that has not been given one yet. `WALLS` holds the six refusal
strings, and a test pins each against the Python constant that would be sent,
so the words a person reads before the click and the words the server sends
cannot drift.

**The job field.** `job` is on the account record with `unset` as the default,
so every record that predates it reads unset and nobody's access or screen
changed. Thirteen values, `auth_store.JOBS`, in the same order as
`session.js`'s `JOBS`, pinned by a test:

| Job | Door | Job | Door |
|---|---|---|---|
| `general_manager` | `today` | `campaign_manager` | `clients.campaigns` |
| `planner` | `plan.week` | `analyst` | `clients.money` |
| `scheduler` | `plan.day` | `data_steward` | `sources.today` |
| `traffic_operator` | `plan.tonight` | `account_administrator` | `account.accounts` |
| `programming_representative` | `rules.restrictions` | `model_steward` | `model.console` |
| `compliance_owner` | `rules.licence` | | |
| `yield_owner` | `rules.rate_card` | | |
| `account_manager` | `clients.all` | | |

Thirteen doors, no two roles sharing a first screen. `DOORS` is complete and
freezes with the file: a later piece implements the route for its own door id
and adds nothing to the map. `doorFor(session)` returns `today` for an unset
job and for a channel account whose job is the company-only one, so nothing
tells a channel account the other side exists. `jobPickerRows(session, locale)`
is the picker card's contract: 13 rows for a company account, 12 for a channel
account, each `{id, door, label, doorLabel}`. `needsJobPicker(session)` is
false when login is not set up, because there would be no record to write to.

**`PUT /api/auth/job`**, body `{"job": "planner"}`, returns the account record.
Self-service by design: a job decides a landing screen, not a permission, so it
sits outside `/api/auth/users*` and a viewer may set their own. An unknown
value answers 400 and changes nothing. An administrator may also set `job` in
the `POST /api/auth/users` body; it is optional and defaults to `unset`.

The account payload gained exactly one key. It is now `username`,
`display_name`, `role`, `created_at`, `must_change_password`, `affiliation`,
`job`.

## Rule 5: the guardrails and the activation switch

`kairos_api/guardrail_store.py` with `data/regulatory_guardrails.json`.

```python
from kairos_api import guardrail_store

body = guardrail_store.payload(request)                  # the read, with can_edit
guardrail_store.require_guardrail_editor(request)        # the distinct permission
guardrail_store.record_change({"max_breaks_per_hour": 3}, effective="2026-09-01",
                              actor=username, reason="regulator circular")
```

The store holds the four numbers that are the licence:
`max_ad_minutes_per_hour` 12.0, `max_breaks_per_hour` 4,
`min_break_spacing_minutes` 7, `protected_program_max_ad_minutes_per_hour` 8.0,
with `effective_date` 2026-06-14 and `source_url` https://www.rashut2.org.il/.
Every one of those is the value `KairosSettings` ships, and a test fails if the
two drift while both exist.

- **The effective date.** `values_on(day)` answers what the limits were or will
  be on any day. `effective_date(day)` names the day the limits in force took
  effect. A change recorded today for next month does not move a number today.
- **The change record.** `record_change` appends `{effective_date, recorded_at,
  actor, reason, values, before}` and writes atomically. The log is append-only
  and `changes()` returns it oldest first. `changed_since(day)` is the
  attestation answer: an empty list is the evidence that no guardrail moved.
  `scheduled_changes(day)` is the alert: a limit about to move is visible
  before the day it moves.
- **The distinct permission.** `GUARDRAIL_WALL` is role-gated on `admin` and
  not gated on affiliation, because the limits are the operator's own licence:
  a channel account reads them, an admin changes them, and the operator who can
  move the revenue slider cannot move the licence. The refusal is
  `עריכת מגבלות הרגולציה שמורה למנהל המערכת`.
- **Values are validated** against the same bounds `KairosSettings` declares,
  so a value refused there is refused here. A refused change leaves no trace.

**The cutover, for P5, is one line.** `settings_overlay(settings)` returns the
settings with the four values in force applied and every other field untouched.
It is an exact identity today, proven on both the shipped defaults and the
deployed `data/kairos_settings.json`, so adopting it moves no number. Until it
is adopted, `KairosSettings` keeps the four fields and `GET /api/settings`
answers exactly what it answered before this piece.

`kairos_api/model_activation.py` is the audience model activation switch.

```python
from kairos_api import model_activation

body = model_activation.payload(request)             # the read, with can_edit
model_activation.set_active(True, request)           # the gated write
```

`payload` returns `{field, active, state, computed_at, consequence_he,
consequence_en, can_edit}` plus `can_edit_reason` when refused. `state` is the
engine's own three-state basis: `off`, `on`, `on_no_artifact`. It carries no
gate verdict, no coverage, no coefficient and no p-value, and a test greps the
payload against the section 4.2 lexicon, so this stays true.

`ACTIVATION_WALL` is company-only with the Hebrew denial
`הפעלת מודל הקהל שמורה לצוות החברה`, built exactly like the event pricing
denial beside it. `set_active` saves through the same settings seam every other
configuration act uses, so the freshness fingerprint sees the flip and the
saved plan is marked out of date exactly as it is today.

Both stores hand over to **P5**, not to P7. The switch is a run-side
configuration act and its surface is Rules. P7 renders a read-only mirror and
owns no control.

## What this piece deliberately did not do

- **It did not scope a route.** `/api/schedule` and `/api/break-operations` are
  P2's and P3's. The helper and the measurement are here; the edit is theirs.
- **It did not close `GET /api/parameters`.** It is on nobody's row in section
  8.2 and it is served from a module this piece does not own. It needs a ruling
  before it can be walled.
- **It did not remove the four guardrail fields from `KairosSettings`.**
  Removing them changes `GET /api/settings`, which is a visible change in a
  refactor wave. The store is authoritative from the moment P5 calls
  `settings_overlay`, and the drift test keeps the two honest until then.
- **It did not add the `core.py` compatibility shim.** The shim exists to keep
  readers importing unchanged when the fields leave `KairosSettings`. Nothing
  has left, so nothing needs shimming, and `core.py` is already 698 lines,
  which is over the file-size cap.
